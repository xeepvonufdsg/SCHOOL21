### Как учиться в «Школе 21»

- «Школа 21» может быть не похожа на тот образовательный опыт, который случался с тобой ранее. Это обучение отличает высокий уровень автономии: у тебя есть задача, и ее необходимо выполнить. На протяжении всего курса ты будешь самостоятельно добывать информацию, чтобы углубиться в тему и решить задачу. Пользуйся всеми доступными средствами поиска информации — ресурсы интернета неограниченны. Внимательно относись к источникам информации (например, если используешь нейросети): проверяй, думай, анализируй, сравнивай.
- Тебе необходимо презентовать свое решение другим учащимся и получить от них обратную связь. Взаимообучение (P2P, Peer-to-Peer) — это процесс, при котором учащиеся обмениваются знаниями и опытом, выступая одновременно в роли учителей и учеников. Этот подход позволяет учиться не только у преподавателя, но и друг у друга, что способствует более глубокому пониманию материала.
- Смело проси о помощи: вокруг тебя такие же пиры, которые тоже проходят этот путь впервые. Не бойся откликаться на просьбы о помощи. Твой опыт ценен и полезен, смело делись им с другими участниками. Присоединяйся к Rocket.Chat, чтобы получать свежие анонсы от сообщества.
- Твое обучение не будет иметь никакого смысла, если ты будешь копировать чужие решения. Если пользуешься помощью других — всегда разбирайся до конца, почему, как и зачем. Не бойся ошибиться.
- Если ты на чем-то застрял и кажется, что ты уже все перепробовал, но все равно непонятно, куда идти, — просто передохни! Поверь, этот совет помогал многим специалистам в их работе. Проветрись, перезагрузи голову, и, возможно, в следующий раз тебе наконец придет нужное решение!
- Важен не только результат обучения, но и сам процесс. Нужно не просто решить задачу, а понять, КАК ее решить.

## Chapter III

### 1.1. User Story Map

User Story Map представляет собой визуальный инструмент для организации пользовательских историй в логический порядок. Он помогает команде проекта лучше понять требования пользователей и создать структурированный план для разработки продукта.

User Story Map состоит из двух основных компонентов:

- вертикальной оси (эпики, задачи и пользовательские истории);
- горизонтальной оси (ценность для пользователей).

**Пример:**

> *Предположим, мы разрабатываем приложение для заказа еды онлайн. На вертикальной оси (Y) могут быть слои, представляющие действия, задачи пользователя и пользовательские истории. По горизонтальной оси (X) располагаются сценарии, такие как «Регистрация пользователя», «Выбор продукта», «Оплата» и т. д. User stories соответствуют каждому сценарию и размещаются в соответствующих ячейках User Story Map.*

User story позволяет в том числе определить Minimal Viable Product (MVP) — минимально жизнеспособный продукт, сфокусироваться на важных функциях и постоянно улучшать пользовательский сценарий.

**Шаги по составлению User story:**

1. **Выбрать инструмент для визуализации.** (В дальнейшем мы будем использовать [Miro](https://miro.com/ru/), но можно использовать и другие инструменты, например, [Trello](https://trello.com) или [Cardboardit](https://cardboardit.com)).
2. **Собрать команду**, которая будет работать над проектом. Обязательно привлечь владельца продукта, чтобы он поделился своим видением.
3. **Провести мозговой штурм.** Команда обсуждает свои идеи. Результатом мозгового штурма должна стать User story по шагам — что делает пользователь, когда использует продукт.
4. **Расставить приоритеты.** Решите, какой функционал важно иметь уже на этапе запуска проекта, а какие пользовательские действия можно реализовать позднее. Такие решения менеджер не может принимать самостоятельно, важно согласовать со стейкхолдерами.
5. **Провести проверку.** В конце мозгового штурма сделайте небольшой перерыв и вернитесь к просмотру User story со свежим взглядом. Важно убедиться в том, что все члены команды понимают карту одинаково.
6. **Применить полученные результаты.** По итогу у вас уже есть готовый бэклог (возможно, не максимально декомпозированный, но уже понятный для всех), с которым команда может работать. В процессе могут возникать корректировки — это естественный процесс. User story можно изменять, если появляются новые вводные.

Программные продукты это не только приложения для покупателей, гостей и клиентов, но и внутренние инструменты для тех. поддержки, бухгалтерии и юристов. Инструмент User Story Mapping универсален, просто подставь действующим лицом пользователя твоего сервиса и продолжи формировать карту.

Составление карты пользовательских историй помогает на начальных этапах понять вектор развития проекта, определить ключевой функционал и сформировать бэклог команды.

### 1.2. Бэклог. Формирование бэклога с помощью User Story Map

С понятием «бэклог» ты уже столкнулся на первых уроках. Сейчас мы еще раз систематизируем полученные ранее знания и дополним их чем-то новым.

Бэклог — это список задач, требований и функциональностей продукта, которые должны быть выполнены в ходе разработки проекта. Бэклог составляется на основе пользовательских историй и служит основой для планирования и управления проектом.

**Пример:**

> *Предположим, у нас есть список пользовательских историй для разработки приложения для заказа еды онлайн. Бэклог может включать следующие задачи:*
>
> - *Добавить функцию регистрации пользователя.*
> - *Разработать страницу выбора блюд.*
> - *Интегрировать платежную систему и т. д.*
>
> *Бэклог помогает команде проекта иметь ясное представление о том, какие задачи нужно выполнить, и планировать их по приоритету.*

С помощью User Story Map мы можем формировать бэклог. Анализируя каждый пользовательскую историю, мы можем идентифицировать проблемные области, требующие улучшений, и добавлять соответствующие задачи в бэклог.

Способ User Story Mapping очень хорош своей простотой и возможностью формализации процесса формирования бэклога и расстановки приоритетов. Также он позволяет концентрироваться на пользовательском опыте, а не на требованиях стейкхолдеров и инвесторов.

1. Вдоль горизонтальной линии размещаются либо эпики, либо серия пользовательских историй. Это позволяет подумать о том, как пользователи, например, перемещаются по продукту — от регистрации до настройки своего профиля и использования определенных функций или от момента входа на сайт онлайн-магазина до оплаты товара.
2. Затем вдоль вертикальной оси эпики декомпозируются на конкретные задачи, решение которых будет улучшать продукт после каждой итерации. При этом задачи, которые по оси находятся выше, имеют больший приоритет в сравнении с теми, что находятся ниже.
3. После этого можно провести горизонтальную ломаную линию, которая делит все задачи на релизы (или спринты, если проект небольшой).

В общих чертах карта пользовательских историй состоит из следующих элементов:

- Путь пользователя — по горизонтали.
- Эпики или пользовательские истории — вдоль пути следования пользователя.
- Ранжированные по приоритету выполнения задачи, которые являются частями пользовательской истории, — по вертикали.

Важнейшими преимуществами такого подхода являются:

- **Визуализация**: дает понимание всем участникам процесса, какую систему мы разрабатываем и какие у нее ключевые возможности.
- **Порядок формирования релизов**: система показывает, в какой релиз какая пользовательская история попадет.

User Story Mapping подходит для создания MVP. Но использование данного метода для больших и динамичных продуктов стоит ограничить: полученная в таком случае система окажется слишком громоздкой.

### 1.3. Разработка API-документации на основе User Story

Люди общаются, передавая информацию письмом или устно, а сервисы взаимодействуют (в основном) с помощью API.\
API (Application Programming Interface) – набор правил и описаний, по которым одна программа может:

- отправить запрос (что ей нужно),
- получить ответ (результат или ошибку),
- и сделать это в определённом формате (чаще всего — JSON через HTTP).

Есть несколько разных типов API, мы в данном курсе будем говорить о наиболее часто используемом – REST API.

**Пример:**

> Чтобы отобразить, какие позиции представлены сегодня в меню, приложение для заказа еды обращается на сервер и запрашивает список доступных блюд: \
> GET <https://dontsleepeat.api/v1/Menu>. \
> Далее, при заказе еды, приложение передает на сервер все данные пользователя: \
> POST <https://dontsleepeat.api/v1/OrderCreate>, а в ответ получает от сервера подтверждение, что заказ принят, после чего отображает эту информацию на экране. Таким образом, приложение (клиент) общается с сервером с помощью заранее написанных запросов-ответов, они и называются API-методы.

В этом примере эти ссылки <https://dontsleepeat.api/v1/Menu> и <https://dontsleepeat.api/v1/OrderCreate> это HTTP запросы методов, то есть их техническое форма обращения к API.

**Основные типы методов (HTTP-запросов):**

- **GET** – это метод запроса, для получения данных. *Например, отобразить в личном кабинете данные пользователя или вывести меню на главный экран.*
- **POST** – это тип метода для добавления информации в БД. Создание заказа или авторизация (создание записи в журнале авторизации).
- **PUT** – это редактирование данных в БД. *Например, изменение возраста пользователя или времени доставки товара.*
- **DELETE** – это метод для удаления чего-либо – пользователя, заказа, почты, товара и тд.

User story описывает поведение системы с точки зрения пользователя. API — средство обеспечить это поведение программно. Мы можем использовать User Story, чтобы спроектировать документацию для API-методов, то есть определить набор методов, что будет в запросе и что ожидается в ответе. Разработкой такой документации всегда занимается сторона, к которой обращается клиент, где хранятся и обрабатывается данные.

**Как проектировать API-документацию на основе User Story:**

1. Для каждой User Story определи действие. Например, «Как пользователь, я хочу войти в систему, чтобы видеть свои заказы».
2. Преобразуй каждое действие пользователя в функцию программы, *например:*

| User Story | Что делает программа |
| --- | --- |
| Зарегистрироваться | Создать нового пользователя |
| Войти в систему | Проверить логин и пароль, выдать токен |
| Отменить заказ | Изменить статус заказа на “отменён” |

1. Определи тип HTTP-запроса для каждого метода – GET / POST и тд.
2. Придумай название для каждого метода, это будет его адрес. *Например, UserAdd, OrderDelete.*
3. Определи входные и выходные данные для каждого метода. Для регистрации нужны пользовательские данные, для создания заказа– адрес доставки и время.
4. Определи права доступа для каждого метода.

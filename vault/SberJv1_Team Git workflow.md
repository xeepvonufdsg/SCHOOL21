## Как учиться в «Школе 21»

- Здесь тебя ждет уникальный образовательный опыт с большим количеством свободы. Ты получаешь задачу и самостоятельно ищешь пути решения, используя любые удобные способы поиска информации — ресурсы интернета или нейросети (например, GigaChat). Но внимательно относись к качеству информации: проверяй, думай, анализируй, сравнивай.
- Взаимообучение (Peer-to-Peer, P2P) — это обмен знаниями и опытом с другими пирами, где каждый выступает и учителем, и учеником. Такой подход позволяет глубже понять материал, учась друг у друга.
- Чувствуй себя свободно и проси о помощи — вокруг тебя те, кто тоже впервые проходят этот путь. Делись своим опытом и идеями с другими. Присоединяйся к RocketChat, чтобы быть в курсе всех новостей от нашего сообщества.
- Твое обучение не будет иметь никакого смысла, если ты будешь копировать чужие решения. Если пользуешься помощью других — всегда разбирайся до конца, почему, как и зачем. Не бойся ошибиться.
- Кажется, что задача невыполнима? Сделай перерыв, проветрись, перезагрузи голову — это помогало многим. Возможно, после этого решение придет само собой.
- Важен не только результат обучения, но и сам процесс. Нужно не просто решить задачу, а понять, КАК ее решить.

Как работать с проектом:

- Перед выполнением проект необходимо склонировать с GitLab в одноименный репозиторий.
- Все файлы необходимо создавать в папке `src/` склонированного репозитория.
- После клонирования проекта необходимо создать ветку `develop` и вести разработку в ней. После этого пушить в GitLab также нужно ветку `develop`.
- В твоей директории не должно быть иных файлов, кроме тех, что обозначены в заданиях.

## Введение

На этом этапе обучения в «Школе 21» ты уже наверняка уверенно работаешь с системой хранения версий git. git — это сердце Gitlab — платформы для коллективной работы над кодом. В Сбере git также используется: в рамках Bitbucket и платформы собственной разработки SourceControl.

В этом проекте практически не будет информации о командах git — все это ты можешь найти [здесь](https://git-scm.com/book/en/v2).

Этот проект про корректное и профессиональное использование git при командной разработке. В одиночку ты можешь сделать pet-проект или даже прототип для стартапа, но в крупных компаниях типа Сбера разработку сервиса всегда ведет команда.

Командная работа с git предполагает определенные правила:

1. Все задачи фиксируются в таск-трекере, и каждый код должен быть связан с конкретной задачей или баг-репортом.
2. Над кодом сервиса одновременно могут работать несколько разработчиков, не создавая конфликтов.
3. Параллельно может вестись разработка нескольких версий сервиса.
4. История изменений должна четко отражать авторство кода для возможности оперативного уточнения деталей реализации.
5. Все изменения кода должны сопровождаться понятными, осмысленными комментариями.
6. Попадание кода в релиз происходит через процедуру код-ревью, сочетающую автоматизированные проверки и ручной анализ.

Правила лучше всего усваиваются через практику. У тебя есть 10 заданий, направленных на погружение в разные аспекты командной разработки в git и тренировку навыка:

1. Настройка `.gitignore`.
2. Настройка информации об авторе commit в git.
3. Формат перевода строки в текстовых файлах в git.
4. Что можно хранить в git.
5. Основные модели ветвления: GitFlow, GitHub flow, GitLab flow, Trunk Based.
6. Best practices по работе с ветками.
7. Best practices по commit messages.
8. Best practices по работе с pull requests.
9. Атомарные commit и pull requests.
10. Разделение и объединение commit.

Результат выполнения каждого задания оформляй в виде commit-а в текущем проекте. Разрабатывать будем калькулятор, отдающий результат по REST API.

### Задание 1. Настройка `.gitignore`

Не все файлы нужно хранить в git. Что исключить? Зависит от среды разработки и языка, но точно можно выделить следующие категории.

**Что не рекомендуется хранить в git:**

- временные файлы,
- результат сборки,
- персональные настройки,
- любые другие файлы, которые не нужны другим участникам команды и не нужны для сборки проекта в CI-системе.

Нет необходимости выбирать вручную при commit-е эти файлы, т.к. git-клиент умеет автоматически исключать ненужные файлы. Для этого укажи маски ненужных файлов в `.gitignore`. Этот файл можно разместить в любой папке проекта (он действует рекурсивно), но обычно его кладут в корень.

`.gitignore` часто создается автоматически: современные платформы для работы с кодом и IDE (IntelliJ IDEA), онлайн-генераторы или AI-помощники могут сгенерировать базовый вариант, который можно улучшать. Если ты видишь, что у тебя в проекте появились ненужные другим участникам команды файлы — добавляй их в `.gitignore`.

### Задание 2. Информация об авторе commit в git

Когда ты отправляешь изменения в коде на сервер, вместе с кодом отправляются и метаданные: текстовое описание commit и данные об его авторе.

Эти данные не используются для аутентификации, но должны быть достоверными.

При командной разработке рекомендуем всегда указывать актуальные данные автора, потому что это:

- позволяет быстро идентифицировать разработчика для синхронизации правок или обмена опытом, особенно когда над проектом работает достаточно большая команда;
- многие системы коллективной работы с кодом позволяют настроить проверку того, что email (и, возможно, имя) автора commit-а совпадает с данными учетной записи;
- это гарантирует точность информации об авторе: если такая проверка настроена, при несовпадении данных push на сервер будет отклонен.

### Задание 3. Формат перевода строки в текстовых файлах

Разработчики даже внутри одного проекта могут использовать разные ОС (Windows, macOS, Linux), где различаются символы перевода строки. Если у тебя есть опыт переноса текстовых файлов из Windows в Linux, наверняка ты понимаешь, о чем речь. Ты легко можешь столкнуться с проблемой читаемости кода при переносе файлов между системами. Git решает эту проблему, автоматически конвертируя переводы строк при получении и отправке кода.

В Сбере происходит переход на SberOS (собственная версия Linux), но твой код все равно могут просматривать в Windows, поэтому, как разработчику, тебе важно хорошо ориентироваться в форматах перевода строки в текстовых файлах.

### Задание 4. Что можно хранить в git

Ты уже знаешь, какие типы файлов стоит сразу исключить при добавлении commit в git. Давай теперь рассмотрим его на уровне выше: что стоит держать в проекте вместе с исходниками, а что нет?

Git хранит всю историю изменений всех файлов проекта, всегда может показать diff — изменение по отношению к предыдущей версии. Этот diff можно переслать коллеге.

Код-ревью — это по сути изучение diff-ов. Очевидно, что diff-ы хорошо работают с текстовыми файлами. Проводить ревью изменений в бинарном файле невозможно.

**Типичные ошибки начинающего разработчика или типы файлов, которые не стоит хранить в git:**

- Зависимости проекта:

  Для их хранения используй менеджеры репозиториев. Самый известный — Maven Central, из которого ты сейчас выкачиваешь необходимые зависимости. У него есть альтернативы, которые можно развернуть локально (внутри компании) — Nexus и Artifactory.

  В Сбере все зависимости загружаются из внутреннего Nexus. Внешние зависимости без поддержки менеджера — повод задуматься об их использовании. Если зависимость разрабатывается внутри команды — аналогично, ее можно закачать в локальный репозиторий компании. Если зависимость внешняя, но не хранится в известном менеджере репозиториев — стоит задуматься над ее применением, т. к. непонятно, кто ее будет поддерживать.
- Контент:

  Для хранения, а главное, управления контентом также используй специальные системы — CMS (Content Management System).

  Преимущество хранения контента в CMS в том, что его можно доставлять на ПРОМ (PROD) независимо от релизов приложения.
- Любые бинарные файлы:

  Да, у этого правила могут быть исключения. Если ты разрабатываешь веб-сайт, у тебя могут быть изображения, которые являются неотъемлемой частью страницы. Возможно, у тебя есть шаблоны, хранящиеся в бинарном виде. Но это все исключения, лишь подтверждающие правило.

  Git хранит всю историю изменений и при клонировании по умолчанию скачивает ее полностью по всем веткам.

Если в репозитории есть большие бинарные файлы, то:

- Время клонирования будет увеличиваться.
- Контрольная сборка на CI-сервере будет занимать больше времени.
- Со временем клонирование может «падать» из-за таймаутов.
- Git-сервер начнет тормозить при любых операциях (конечно, для серьезных проблем размер проекта должен весить десятки гигабайт).

Но в целом Git не предназначен для работы с большими файлами.

### Задание 5. Основные модели ветвления: GitFlow, GitHub flow, GitLab flow, Trunk Based

Чтобы команда могла эффективно работать над проектом, ей необходимо договориться о четких правилах по наименованию и порядку слияния веток проекта.

Каждый член команды должен понимать, в какой ветке лежит та или иная фича, где лежит стабильная версия кода, где лежит код конкретного релиза.

Эта информация будет полезна твоим коллегам и пригодится для настройки прав доступа в проекте. Например, чтобы запретить прямые изменения в ветке без pull request или удалить ветки с важным кодом.

Есть ряд моделей ветвления для git, которые упрощают процесс совместной разработки.

**GitFlow**

Самая известная. Она достаточно сложна, разделяет ветки на 6 типов и определяет правила их слияния. GitFlow лучше всего подходит для open source проектов с большим числом участников, версий и сложным процессом код-ревью. Для обычного проекта эта модель может оказаться излишне громоздкой: например, ветка master не всегда нужна, если есть релизные ветки.

**GitHub flow, GitLab flow**

Модели, созданные для упрощения разработки по сравнению с GitFlow, разработанные командами соответствующих платформ для совместной работы с кодом — GitHub и GitLab. Они проще и используют меньше типов веток. Если ты работаешь с GitHub или GitLab, стоит попробовать рекомендованную ими систему ветвления.

**Trunk Based**

Эта модель может показаться выбором новичка — одна ветка, все коммиты идут в нее. Но на самом деле это подход опытных разработчиков с отлаженным процессом код-ревью в команде. Trunk Based предполагает отложенное код-ревью, что накладывает повышенную ответственность на каждого разработчика.

В Сбере нет единого стандарта для моделей ветвления git. Чаще всего используется упрощенный GitFlow — без веток master и hotfix. Иногда встречается вариант с несколькими develop-ветками — если у команды часто одновременно идет разработка нескольких релизов.

На самом деле, важно не строгое следование конкретной модели ветвления, а следующее:

- выбрать подходящую модель ветвления для проекта;
- описать ее в документации (например, в `readme.md`);
- настроить систему контроля версий так, чтобы она не позволяла создавать ветки, не соответствующие выбранной модели, и вливать код с нарушением ее правил.

1. *Какие общеизвестные модели ветвления ты знаешь, чем они отличаются?*
2. *Чем хороша и плоха GitFlow?*
3. *Какую модель ты бы выбрал для простого бизнес-сервиса, разрабатываемого 3 разработчиками, и почему?*

3. Твоя вторая фича — метод для вычитания. Пройди с ней аналогичный путь по GitHub flow.

### Задание 6. Best practices по работе с ветками

Что важно знать про наименования веток.

Есть 2 типа веток по названиям:

1. Ветки с фиксированными названиями — определяются моделью ветвления — develop, main, trunk — их названия стандартны и не вызывают вопросов.
2. Ветки, имена которых зависят от разрабатываемой фичи, бага или релиза.

Основные правила именования:

1. Ветка с доработкой или исправлением бага должна содержать номер тикета в названии. Некоторые платформы для совместной разработки проверяют соответствие тикету в таск-трекере — если его нет, push не пройдет. Да, feature-ветки живут недолго, но пока команда ведет с ними работу, название должно указывать на связанную задачу. *Пример: feature/TASK-42*.
2. Релизная ветка должна включать номер релиза, совпадающий с версией дистрибутива (без build number). Главное — точное соответствие, включая нули. Это правило гарантирует четкую связь между релизом и веткой, из которой он собран. *Пример: release/1.0.0*.

Дополнительные рекомендации по работе с короткоживущими ветками:

- После слияния изменений в основные ветки (develop, main, release) временная ветка должна быть удалена. Все изменения в виде цепочки commit останутся в целевой ветке.
- Хранение старых веток затрудняет навигацию и поиск.
- Многие платформы позволяют автоматически удалять исходную ветку после слияния с целевой.

**ВОПРОСЫ, КОТОРЫЕ ТОЧНО ЗАДАСТ ТВОЙ ТИМЛИД:**

1. *Какие правила следует соблюдать при наименовании feature-ветки?*
2. *Какие правила следует соблюдать при наименовании release-ветки?*
3. *Нужно ли сохранять feature и bugfix-ветки в системе контроля версия навсегда и почему?*

**Результат:**

1. Заведи задачу в GitLab по добавлению метода умножения двух чисел. Создай feature-ветку, содержащую реализацию данной задачи. Соблюдай правила наименования.
2. Влей созданную ветку в основную ветку через pull request. Удали feature-ветку.

### Задание 7. Best practices по commit messages

Commit message — это текстовые метаданные, которые сопровождают каждый commit.

Git не позволяет делать commit без сообщения и не ограничивает объем сообщения. Конечно, при коллективной разработке важен не размер сообщения, а его суть.

Часто ли тебе приходилось сталкиваться в commit message с формальным текстом, никак не описывающим суть доработки?

```
🔴 «fix» — формальное сообщение;    
🟢 «исправлены таймауты по умолчанию» — содержательное сообщение.
```

**Почему важно писать осмысленные commit messages?**

1. Мы читаем код чаще, чем пишем его.

   История изменений в ветке, выводимая по git log, — часть документации, которая помогает понять историю и развитие проекта.
2. Из истории commit можно автоматически сформировать release notes — краткое описание изменений в текущем релизе.
3. На ручном код-ревью информативный текст commit ускоряет понимание сути доработки.

Материалы о правилах формирования commit ты легко можешь найти самостоятельно. Самый известный стандарт формирования commit messages [здесь](https://www.conventionalcommits.org/en/v1.0.0/).

***В Сбере тоже есть внутренние рекомендации к созданию commit messages.***

Проверь себя: скольким пунктам ответил бы твой стандартный commit?

|  |  |
| --- | --- |
| В начале commit message — ID задачи из таск-трекера, отделенное пробелом или знаком препинания. | Сообщение содержательное, а не формальное. |
| Сообщение содержит заголовок, все остальное — опционально. Части разделены пустой строкой. | Язык сообщения — русский, т. к. Сбер — российская компания. |
| Вместо личной формы «исправил», «исправила» используй страдательные формы глаголов: «исправлено», «добавлено», «обновлено».  Это лишняя информация об авторе, она сохраняется отдельно в истории изменений. | Длина сообщения соответствует правилу 50/72. |
| В сообщении отражена цель изменений, а не детали реализации. Исключение — детали нужны для понимания сути. | Без указания имени класса (т. к. имена меняются). |

При работе с кодом ты создаешь три типа объектов:

- ветки,
- commit,
- pull requests.

И если большинство веток удаляется после слияния, а описание влитого pull request можно посмотреть (но делают это редко), то текст commit остается с проектом навсегда.

Далее ты узнаешь, как можно исправить сообщение, если что-то пошло не так.

\*Кстати, одно из перспективных применений AI — генерация commit messages на основе изменений в коде.

**ВОПРОСЫ, КОТОРЫЕ ТОЧНО ЗАДАСТ ТВОЙ ТИМЛИД:**

1. *Почему важно корректно написанное commit message?*
2. *Что должно быть в commit message?*
3. *Что не так с сообщением: «Внес мелкие правки», и почему его недостаточно для осмысленного commit?*

**Результат:**

1. Новая задача — метод деления с остатком. Создай commit, исходя из правил выше, message которого содержит только заголовок.
2. Следующая задача — метод деления без остатка. Оформи commit по правилам, но уже с заголовком и телом.
3. Открой историю изменений в консоли и в GitLab. При работе в консоли используй разные варианты отображения истории. Что ты можешь понять о процессе развития сервиса из истории?

### Задание 8. Best practices по работе с pull requests / merge requests

Pull requests и merge requests — одно и то же. Это запрос на слияние одной ветки с другой. В большинстве команд pull request — обязательное условие для вливания изменений в стабильную ветку, так как он позволяет провести код-ревью.

Почему ручное код-ревью — сложная задача?

- Ревьювер часто делает это параллельно с собственной работой.
- Переключаться между задачами сложно.
- Нужно разобраться в сути твоей задачи, оценить архитектуру и алгоритмы.

Работая в команде, твоя задача как автора pull request — облегчить ревью.

Как? Через правильное именование веток и commit message. Добавим к этому правильное оформление pull requests.

Основные правила оформления pull requests:

1. В заголовке pull request указывай ID задачи из таск-трекера (все по тем же, рассмотренным выше причинам) + краткую суть изменений.
2. Добавляй ревьюверов только когда pull request «готов к ревью». Можно использовать метку, которая покажет, что PR еще не готов.
3. Перед внешним ревью проведи внутреннее:\
   а) проверь, что в pull request не попало ничего лишнего и наоборот;\
   б) убедись, что код собирается, тесты проходят, исправь замечания статического анализатора кода;\
   в) оцени commit message — понятна ли по ним суть изменений;\
   г) при необходимости влей последние изменения из стабильной ветки;\
   д) исправь merge-конфликты, если они есть.
4. Если в commit messages недостаточно информации, добавь описание к pull requests.
5. Отвечай на все замечания ревьювера. После исправления ошибки дополнительно ответь «исправлено».
6. Думай, как облегчить ревьюеру проверку: подключи автоматическое форматирование в IDE.
7. Самое главное — не делай слишком большие pull requests. Об этом подробнее в следующих заданиях.
8. После одобрения автор отвечает за вливание и закрытие неактуальных pull requests.

**Как профессионально относиться к замечаниям ревьювера:**

- Замечания ревьювера — это не критика лично тебя, а комментарии к коду. Не стоит обижаться, лучше разобраться в них.
- Если ревьюверу что-то непонятно, скорее всего, это будет непонятно и другим в команде.
- Спорные вопросы решайте «голосом» — так быстрее достигнете взаимопонимания.

### Задание 9. Атомарные commit и pull requests

***В рамках командной разработки у тебя появились две новых задачи: добавить в калькулятор расчет тригонометрических функций: sin, cos, tg и исправить ошибку в ранее добавленном методе логарифма (оказалось, аналитик ошибся и перепутал ln с log).***

Задачи кажутся простыми, верно? Как ты распределишь их по pull requests и commits?

Из названия Задания 9 ты, вероятно, уже понимаешь, что речь будет идти об атомарности.

Атомарная операция (от греч. άτομος — «неделимое») — это операция, которая выполняется полностью либо не выполняется вообще.

Чтобы commit или pull request были атомарными, они должны содержать только тесно связанные изменения. Которые или вливаются в очередной релиз целиком, или целиком откатываются.

**Зачем это нужно?**

- Упрощение код-ревью

  Ревью чужого кода — сложная задача. Несколько задач в одном pull request усложняют ее еще больше.
- Легкий откат изменений

  Если фича в отдельном commit, ее легко удалить, в случае если команда решит отказаться от нее.
- Обмен знаниями

  Отдельный commit с типовым решением можно быстро сохранить в diff и отправить коллеге.
- Исправление бага в нескольких ветках

  Если фикс лежит в отдельном commit, с большой вероятностью его легко можно перенести в соседнюю ветку.
- Поддержание высокой скорости изменений

  Даже простая дополнительная задача может затянуться и сорвать сроки основной.

### Задание 10. Разделение, объединение и переименование commit

Бывает, что в работе разработчика случаются ошибки:

- Лишний код в commit.
- Забыл добавить файл и узнал об этом на код-ревью.
- Неудачно написал commit message.
